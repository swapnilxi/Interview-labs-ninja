CCAF Exam Guide · Domain 3: Configuration & Memory

Where Should Team Rules Live?
Claude Code Memory Scopes, Explained

A senior developer's conventions work perfectly on their laptop — and nowhere else. This lesson dissects the CCAF exam scenario, maps every memory scope in Claude Code, and teaches the one principle that resolves the whole family of questions: rules live at the scope where they are expected to apply.

Exam focus: CLAUDE.md scopes Key file: project /CLAUDE.md Principle: Scope matching Difficulty: Foundational → Applied
01

The Scenario

Exam Prompt

A senior developer on your team has been using Claude Code with a set of coding conventions stored in their personal ~/.claude/CLAUDE.md. The rest of the team wants the same behavior across the repository. New engineers report that Claude Code behaves differently on their machines. What is the correct way to make these team-wide conventions consistently available to everyone?

🎯

The failure is a scope mismatch. The rules are correct — but they live in a user-scoped location while governing a project-scoped concern. The fix is not a bigger context window or a cleverer command. The fix is to move the file to the scope the rule governs.

02

Claude Code Memory Scopes — The Mental Model

Claude Code layers memory from broadest (every project on the machine) to narrowest (a single folder). More specific scopes take precedence, and project-scoped files are the ones that travel with the repository.

Memory scopes in Claude Code — broader on top, more specific toward the bottom. More specific scopes take precedence.
⚠️

Common exam trap: learners conflate "personal file that works on my machine" with "team standard." The exam tests whether you recognize that user scope ≠ project scope, regardless of how good the rules are.

03

The Correct Answer — Deconstructed

Correct

Move the team-wide conventions into a project-level CLAUDE.md in the repository.

Team conventions belong in a project-scoped file that is committed to version control. Every developer who clones or pulls the repository receives the same baseline guidance automatically.

Why it works: The rule is stored at the scope where it is expected to apply. Updates can be reviewed with the code, and behavior becomes reproducible across the team. Personal preferences stay in ~/.claude/CLAUDE.md; team standards move to <repo>/CLAUDE.md. 

# Repository layout — team conventions travel with the code
my-service/
├── CLAUDE.md              # ✅ team-wide conventions, committed
├── .claude/
│   ├── CLAUDE.md          # ✅ alternative project location
│   ├── commands/          # shared slash commands
│   └── settings.json      # shared tool permissions
├── services/
│   └── api/
│       └── CLAUDE.md      # ✅ directory-scoped rules
└── src/

# ~/.claude/CLAUDE.md stays personal — individual preferences only
💡

The exam heuristic: Ask "who needs this rule, and where?" If the answer is "everyone on this repo," the file must be committed at project scope. If the answer is "just me, everywhere," it belongs in user scope.

04

Why the Other Options Fail

Each distractor is plausible but breaks a specific CCAF principle. Learn the failure modes — they repeat across the exam.

Incorrect

Ask every developer to manually copy the senior dev's ~/.claude/CLAUDE.md into their home directory.

Copying a personal file across laptops is fragile and not version-controlled. New developers can miss the configuration entirely, or end up with stale copies.

Failure mode: No single source of truth. It also mixes one user's personal preferences with team-wide standards — future maintenance becomes guesswork.

Incorrect

Create a custom slash command for every coding task so Claude doesn't need project memory.

Slash commands are excellent for repeatable, explicitly-invoked workflows — but they do not replace always-loaded project conventions.

Failure mode: A command must be invoked or selected. Project memory should guide ordinary Claude Code work automatically, without the developer remembering to call anything.

Incorrect

Increase the model's context window so Claude can infer the team's conventions from the codebase.

A larger context window does not solve configuration scope. Claude may infer patterns from code, but it should not have to guess standards that can be stated explicitly.

Failure mode: The issue is not capacity — it is that shared instructions live in the wrong place. Inference is probabilistic; committed instructions are deterministic.

✕ Manual copy

No version control, no review, no reproducibility. Breaks under team growth.

✕ Slash commands only

Opt-in per invocation. Baseline conventions should be always-on, not remembered.

✕ Bigger context window

Capacity ≠ configuration. Rules must be declared, not inferred from noise.

Decision Table — Where Does a Rule Belong?

07

Exam Recap

The single principle that resolves this question family: store the rule at the scope where it is expected to apply.

  • Team conventions → project-scoped, committed CLAUDE.md.
  • Personal preferences → user-scoped ~/.claude/CLAUDE.md.
  • Company policy → enterprise-scoped managed file.
  • Subcomponent rules → directory-scoped CLAUDE.md.
  • Slash commands and larger context windows do not substitute for shared configuration scope.
  • Version control is what makes team rules reviewable, reproducible, and consistent.
