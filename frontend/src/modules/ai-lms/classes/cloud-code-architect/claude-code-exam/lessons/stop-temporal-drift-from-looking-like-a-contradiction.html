Stop Temporal Drift from Looking Like a Contradiction

When your Claude Agent SDK tool reads a wiki page, a README, and a config file written years apart, the same fact shows up with different values. The fix isn't to pick a winner — it's to make time travel with the data.

Learning Objectives

  • Distinguish a genuine contradiction (two current sources disagree) from a temporal difference (one value superseded another).
  • Explain why fetch-time, source-authority heuristics, and averaging all fail as reconciliation strategies.
  • Design a structured agent output schema that carries provenance metadata — publication or last-updated dates — alongside every finding.
  • Apply the "metadata travels with the value" principle to multi-agent context handoff and claim–source mapping.

The Scenario

You're building developer productivity tooling on top of the Claude Agent SDK. The agent explores unfamiliar codebases, reads legacy services, and reports structured findings back to a coordinator. It uses the built-in tools — Read, Write, Bash, Grep, Glob — and pulls documentation from MCP servers.

While mapping a legacy service, the agent reads two sources that describe the same API rate limit:

  • An internal wiki page that says 100 requests per minute.
  • A repository README that says 500 requests per minute.

The agent reports this as a contradiction. It isn't one. The wiki was written in 2021, the README in 2024, and the quota was raised in between. What surfaced as a conflict is really a timeline with a missing axis.

Key Insight

A contradiction requires that two sources claim to be true at the same time. Without dates, a synthesis step has no way to tell "these disagree" from "this one replaced that one." The fix is structural, not heuristic.

The Mental Model

Think of each finding as a point on a number line. Without a time axis, two points look like a scatter — a conflict. With time attached, they line up into a trajectory — a story.

Why the Tempting Fixes Fail

Every "pick one" strategy destroys information the downstream reader needs. Here's the breakdown from the exam scenario:

Strategy Fails because Verdict
Keep the most recently fetched value Fetch time records when the agent read the page, not when the page was true. A stale wiki read last can beat a fresh README. Reject
Average the two values Fabricates a number — 300 rpm — that no source ever documented. Worse than either input in a technical report. Reject
Prefer the "more authoritative" source, drop the other Authority doesn't resolve time. An authoritative but outdated wiki still carries the superseded value, and the evidence of change is lost. Reject
Attach last-updated date to every finding Preserves both values, lets the reader order them chronologically, and reveals the change instead of hiding it. Correct
Common Trap

"Fetch recency" feels like temporal reasoning but is actually event reasoning about the agent, not content reasoning about the source. This is one of the most frequent wrong answers on the CCAF exam.

The Structural Fix: Metadata Travels with the Value

The rule is simple and non-negotiable: any metadata that explains a value must be carried as data alongside that value, because it cannot be reconstructed later. Once the agent has thrown away the wiki's date, no downstream coordinator can recover it.

In practice this means every structured finding emitted by the agent should include a source block with a last_updated field. The synthesis step then reasons over the timeline instead of the raw values.

python 
from dataclasses import dataclass, field
from datetime import date
from typing import Optional

@dataclass
class Source:
    """Provenance metadata that MUST travel with every finding."""
    uri: str
    kind: str                      # "wiki" | "readme" | "code" | "mcp"
    last_updated: Optional[date]   # <-- the field that turns conflict into timeline
    fetched_at: Optional[date] = None  # informational only; never used for ranking

@dataclass
class Finding:
    key: str                # e.g. "api.rate_limit.rpm"
    value: object           # e.g. 100 or 500
    source: Source
    excerpt: str = ""

def synthesize(findings: list[Finding]) -> dict:
    """Order by source date, not by fetch order or perceived authority."""
    dated = [f for f in findings if f.source.last_updated]
    undated = [f for f in findings if not f.source.last_updated]

    dated.sort(key=lambda f: f.source.last_updated)

    return {
        "key": findings[0].key,
        "timeline": [
            {"value": f.value,
             "as_of": f.source.last_updated.isoformat(),
             "source": f.source.uri}
            for f in dated
        ],
        # Never silently drop undated values -- flag them.
        "unverified": [
            {"value": f.value, "source": f.source.uri}
            for f in undated
        ],
        # The current value is the most recent DATED finding.
        "current": dated[-1].value if dated else None,
    }

# Example usage
findings = [
    Finding("api.rate_limit.rpm", 100,
            Source("wiki://legacy-svc", "wiki", date(2021, 3, 4))),
    Finding("api.rate_limit.rpm", 500,
            Source("repo://legacy-svc/README.md", "readme", date(2024, 8, 12))),
]

result = synthesize(findings)
# {
#   "key": "api.rate_limit.rpm",
#   "timeline": [
#     {"value": 100, "as_of": "2021-03-04", "source": "wiki://legacy-svc"},
#     {"value": 500, "as_of": "2024-08-12", "source": "repo://legacy-svc/README.md"},
#   ],
#   "unverified": [],
#   "current": 500,
# }

Notice what this produces: a timeline, not a winner. The report reads "the wiki (2021) says 100, the README (2024) says 500 — the limit was raised." That's a fact about the system's history, which is exactly what a human or coordinator needs to reconcile deliberately.

Tip

When a source has no discoverable date, don't invent one and don't drop it. Bucket it as unverified so the reader knows a value exists without a timeline anchor. Silent omission is the same failure mode as silent picking.

The Deeper Principle

This is the same discipline as claim–source mapping in research agents: every assertion carries its provenance. It's also the same discipline that keeps multi-agent systems honest — when one agent hands context to another, the receiving agent can't re-derive what the sending agent threw away.

For a Claude Agent SDK tool that reads codebases, wikis, and MCP servers, this means the structured output schema is not a formatting concern. It's the reliability boundary. Losing the date field is as bad as losing the value.

Deep Dive

The same failure appears in Kubernetes manifests (last-applied-configuration vs live state), Terraform state (last_refresh vs actual resource), and observability pipelines (metric timestamp vs ingest timestamp). In every case, the answer is the same: never conflate the time you observed something with the time it was true.

Key Takeaways

  • Distinguish a genuine contradiction from a temporal difference — they require different responses.
  • Carry last-updated dates as structured data alongside every finding; metadata that explains a value must travel with it.
  • Never use fetch recency as a proxy for content recency — it records the agent's action, not the source's truth.
  • Never average conflicting values — it fabricates a number no source documented.
  • Never silently drop the losing value — it destroys the evidence that the fact changed.
  • Bucket undated sources as unverified rather than guessing a date or omitting them.
  • The same principle governs Kubernetes state, Terraform refresh, and observability pipelines: observation time ≠ truth time.
