Retry with Error Feedback: Handling Validation Failures in an Agentic CI/CD Pipeline

When a review summary's arithmetic doesn't reconcile, the pipeline must decide: retry, re-prompt blindly, lower the temperature, or escalate to a human. This lesson teaches the classification judgment that separates a self-correctable failure from a missing-grounding failure.

Learning Objectives

  • Classify a pipeline validation failure as self-correctable versus grounding-missing before choosing a remedy.
  • Explain why a retry must carry both the failed output and the concrete validation error to be effective.
  • Distinguish what schema conformance guarantees from what semantic validation must catch.
  • Design a CI/CD feedback loop that pairs structural guarantees with a semantic reconciliation layer.

The Scenario

You're integrating Claude Code into a CI/CD pipeline. On every pull request, the system runs automated code reviews, generates test cases, and posts feedback. Review summaries follow a structured schema like this:

json — review summary schema 
{
  "total_findings": 7,
  "severity_counts": {
    "critical": 1,
    "high":     2,
    "medium":   3,
    "low":      2
  },
  "findings": [ /* ...7 finding objects... */ ]
}

A validation layer flags any summary where total_findings does not equal the sum of the per-severity counts. Here, 1 + 2 + 3 + 2 = 8, but the stated total is 7 — a reconciliation mismatch. The full diff and every finding were present in the original prompt.

The Exam Question

How should the pipeline handle these failures? The correct answer is to retry automatically, sending back the failed summary and the specific count discrepancy, because everything needed to correct it is already in the input.

The Core Judgment: Classify Before You Remedy

The mistake most engineers make is jumping straight to a remedy — retry, re-prompt, lower temperature, escalate — without first asking what kind of failure is this? The classification determines the remedy. There are two failure classes, and they demand opposite responses:

Failure class What it looks like Is the fix derivable from the input? Correct remedy
Self-correctable Format mismatch, structural error, arithmetic inconsistency Yes — all source material is present Retry with error feedback
Grounding-missing Fabricated fact, hallucinated API, invented file path No — the needed source was never provided Supply or retrieve the source, then re-run

An arithmetic inconsistency is squarely in the first class. The model already has every piece of information it needs to re-check its own counts. The discrepancy is a reconciliation error, not a knowledge error.

Key Insight

Retry-with-error-feedback is an application-level validation pattern. It succeeds precisely when the model already possesses everything it needs to produce a corrected answer. The retry isn't a "second chance" — it's a targeted correction task.

The Feedback Loop, Visualized

The mental model is a closed loop: generate → validate → if invalid, feed the failure back → regenerate. The loop only converges when the error signal is passed through. Strip the error signal, and the loop becomes a coin flip.

The dashed red path is the correction loop. It carries the failed output and the specific discrepancy back to the model — that payload is what makes the retry a targeted fix.

Why the Other Options Break the Mechanism

✗ Fresh prompt without the failed summary or error

Withholding the failed output and the error removes exactly what makes retries effective. Without seeing what it produced and what was wrong with it, the model is just as likely to repeat the inconsistency. Error feedback is what turns a retry into a targeted correction. Strip it, and the retry becomes a coin flip.

✗ Rerun unchanged at a lower temperature

Lowering temperature changes token sampling — it does not change the model's arithmetic reconciliation. An unchanged request with no error feedback gives the model no signal about what to fix, so the same inconsistency can recur even at temperature zero.

✗ Route straight to human review without retrying

This misclassifies the failure. Retries are ineffective when the needed information is absent from the provided input. But here the diff and all findings are in the prompt; the model can recount and reconcile the totals. Automatic retry is appropriate before any human involvement — escalating immediately burns human time on failures automation handles well.

The Boundary

When grounding truly is missing, the right move is providing the source material rather than retrying. Retry only helps when the correction is derivable from what the model already has.

Schema Conformance ≠ Correctness

This scenario exposes the boundary of what schema enforcement guarantees. A schema-conformant summary can still be semantically wrong. total_findings being present and correctly typed says nothing about whether it reconciles with the per-severity counts.

Pipelines pair structural guarantees with a semantic validation layer. Extracting both a stated and a calculated value makes discrepancies machine-detectable, so they can feed the retry loop.

This is why patterns like extracting both a stated and a calculated value exist. The validator computes Σ severity_counts independently and compares it to the model's total_findings. When they diverge, that divergence becomes the error signal the retry carries.

Implementing the Pattern

Here's a minimal pipeline handler that classifies the failure, builds a targeted retry payload, and only escalates to humans when the correction genuinely isn't derivable from the input.

python — pipeline handler 
def validate_and_retry(summary, original_prompt, max_retries=2):
    # Layer 1: structural check already enforced by schema.
    # Layer 2: semantic reconciliation.
    stated = summary["total_findings"]
    calculated = sum(summary["severity_counts"].values())

    if stated == calculated:
        return summary  # valid — post to PR

    discrepancy = (
        f"total_findings is {stated}, but the per-severity counts "
        f"sum to {calculated}. Reconcile the total with the findings."
    )

    for attempt in range(max_retries):
        # Retry WITH the failed output AND the concrete error.
        # Both are required — this is what makes it a targeted fix.
        retry_prompt = build_retry_prompt(
            original_prompt=original_prompt,
            failed_output=summary,
            validation_error=discrepancy,
        )
        summary = call_model(retry_prompt)

        stated = summary["total_findings"]
        calculated = sum(summary["severity_counts"].values())
        if stated == calculated:
            return summary

    # Only escalate when correction is NOT derivable from input.
    # For arithmetic inconsistencies, this path should be rare.
    raise NeedsHumanReview(summary, discrepancy)
Deep Dive

Notice the retry payload includes failed_output and validation_error. This mirrors the iterative-refinement principle behind Anthropic's general prompting guidance: give the model a concrete, targeted task — "here is what you produced, here is exactly what's wrong" — rather than a blind second attempt.

Key Takeaways

  • Classify before you remedy. Ask whether the correction is derivable from the provided input before choosing retry, re-prompt, or escalation.
  • Self-correctable failures — format mismatches, structural errors, arithmetic inconsistencies — are fixed by retry-with-error-feedback because the model already has everything it needs.
  • Grounding-missing failures are fixed by supplying or retrieving the source, not by re-prompting.
  • The retry payload must include both the failed output and the concrete validation error. Strip either one and the retry becomes a coin flip.
  • Lowering temperature is not a fix for reconciliation errors — it changes sampling, not arithmetic.
  • Schema conformance ≠ semantic correctness. Pair structural guarantees with a reconciliation layer that computes a value independently and compares it.
  • Escalation is a last resort for self-correctable failures — it burns human time on work automation handles well.
