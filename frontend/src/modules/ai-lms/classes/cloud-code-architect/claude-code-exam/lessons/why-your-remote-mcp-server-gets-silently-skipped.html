Why your remote MCP server gets silently skipped

A single missing field in .mcp.json is enough to make Claude Code drop a perfectly good remote server at startup. This lesson teaches the transport-type mental model that makes the failure obvious — and the fix a one-line change.

9 MIN READ EXAM SCENARIO 2 QUESTIONS

Learning Objectives

  • Distinguish the two transport types Claude Code supports for MCP servers: stdio and http.
  • Identify which fields each transport requires, and what happens when a required field is missing.
  • Recognize the scope rules for .mcp.json (project) vs ~/.claude.json (user) and why scope is unrelated to the failure.
  • Apply the correct fix to a broken remote-server entry under exam time pressure.

The scenario

You are building developer productivity tooling on the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate, and automate repetitive work. It leans on the built-in tools — Read, Write, Bash, Grep, Glob — plus a set of Model Context Protocol (MCP) servers.

An engineer wants the whole team to share a remote MCP server, so they add an entry to the project's .mcp.json with a name and a url — and nothing else. On startup, Claude Code skips the server and logs a configuration error. What change fixes it?

The mental model: type selects the transport

Claude Code's .mcp.json supports two fundamentally different kinds of server entries. The type field is how Claude Code tells them apart, and it determines which other fields are meaningful.

Two transports, two field contracts. type is the switch that picks which contract applies.

Why the broken entry fails

When no type is present, Claude Code assumes stdio — the local-process transport. But a stdio server must be launched, and launching requires a command. An entry that only has a url therefore looks to Claude Code like a stdio server with nothing to run. It cannot start such a server, so it skips the entry and reports a misconfiguration.

Key Takeaway

The type field selects the transport. The transport determines which other fields are meaningful. A url without "type": "http" is a stdio entry missing its command — not a remote entry missing a flag.

The fix

Add "type": "http" to the server entry so the url is interpreted as a remote endpoint.

json · .mcp.json (broken) 
{
  "mcpServers": {
    "team-knowledge": {
      "url": "https://mcp.internal.example.com/sse"
    }
  }
}
json · .mcp.json (fixed) 
{
  "mcpServers": {
    "team-knowledge": {
      "type": "http",
      "url": "https://mcp.internal.example.com/sse"
    }
  }
}

For contrast, here is a valid stdio entry for the same project — note that it has no url, because it never touches the network.

json · .mcp.json (stdio example) 
{
  "mcpServers": {
    "local-lint": {
      "command": "npx",
      "args": ["-y", "@acme/mcp-lint"]
    }
  }
}

Field contract at a glance

Transport Required fields When used Typical scope
stdio command (plus optional args, env) Local tools, per-developer binaries, anything you can npx or run Either — often user scope for personal tooling
http type: "http" and url Shared team servers, hosted services, anything reachable over HTTPS Project .mcp.json — committed and shared
Tip

If you find yourself reaching for a local proxy just to front a remote server, stop. That is a sign you have the transport wrong, not a sign you need more infrastructure.

The three tempting wrong answers

1. "Move it to ~/.claude.json — remote servers are user-scope only."

Incorrect. Remote HTTP servers are fully supported in project-scoped .mcp.json — which is exactly where a shared team server belongs. Moving the entry changes who sees the server (personal rather than version-controlled) without changing how the entry is parsed. The scope of the file has nothing to do with why the entry is being skipped.

2. "Add a command launching a local proxy."

Incorrect. Only stdio entries require a command to launch a local process; an HTTP entry connects directly to its url. A proxy would technically produce a launchable stdio entry, but it solves the wrong problem and adds a process every teammate must install.

3. "Wrap the URL in ${...} environment variable expansion."

Incorrect. Environment variable expansion in .mcp.json exists to keep secrets like tokens out of version control — for example "url": "https://mcp.example.com/sse?token=${MCP_TOKEN}". It does not alter how the transport is interpreted. The entry fails because its transport type is undeclared, not because of how the URL is written.

Warning

Environment variable expansion is a secret-management feature. It is orthogonal to transport selection. If a question mentions ${...} in a transport-error scenario, it is almost certainly a distractor.

Key takeaways

  • type selects the transport. The transport decides which other fields matter.
  • No type → Claude Code assumes stdio → it needs a command.
  • A remote server needs "type": "http" plus a url. Nothing else.
  • Project-scoped .mcp.json fully supports remote HTTP servers — scope is not the problem.
  • A local proxy is the wrong answer whenever the real issue is a missing transport declaration.
  • ${ENV_VAR} expansion is for secrets, not for transport selection. Don't confuse the two.
