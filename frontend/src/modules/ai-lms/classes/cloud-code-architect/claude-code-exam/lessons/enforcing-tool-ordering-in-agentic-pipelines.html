Enforcing Tool Ordering in Agentic Pipelines

Your system prompt says "run tests first." Claude still posts the review comment early. This lesson teaches the one design pattern that closes that gap for good — and why every prompt-based alternative is a coin flip.

Learning Objectives

  1. Distinguish probabilistic guidance (prompts, tool descriptions) from programmatic enforcement (hooks) in an agentic harness.
  2. Explain how a PreToolUse hook intercepts and denies a tool call before it executes, and how the denial reason feeds back to the model.
  3. Identify the anti-pattern of parsing the assistant's natural-language output as a completion gate.
  4. Choose the correct enforcement surface for a given constraint: invariant vs. preference.

The Scenario

A CI pipeline hands Claude a task: run the test suite, then post a review comment summarizing the results. The system prompt is explicit — "Always execute run_tests before calling post_review_comment." Yet in production, Claude occasionally posts the comment first. Tests never ran. The review is ungrounded.

This is not a prompting bug. It is a design bug. The instruction lives in the model's context, which means compliance is a probability — usually high, never 100%. When a single violation has real consequences (a review comment that was never validated), you cannot accept a probability. You need a guarantee.

Key Distinction

Prompts and tool descriptions are suggestions the model usually follows. Hooks are code the model cannot bypass. The first operates inside the model's context; the second operates in the harness, outside the model's control.

The Mental Model: Two Enforcement Surfaces

Picture Claude's decision loop. It reasons, then emits a tool call. Everything in the model's context — system prompt, tool descriptions, conversation history — lives on the left of that boundary. The harness lives on the right. Only the harness can say "no."

How a PreToolUse Hook Guarantees Order

A PreToolUse hook is a callback the harness invokes before a tool call is executed. It receives the proposed tool name and input, inspects session state, and returns a decision. If it denies, the call never runs — and the reason is surfaced back to Claude, which can then take the prerequisite step and retry.

Why This Works

The gate lives in the harness, not in the model's context. Claude cannot "decide" to skip it, forget it, or reword its way around it. Compliance is 100% by construction — not by probability.

Here is a minimal, production-shaped implementation. It records successful run_tests results in session state and denies any post_review_comment that arrives before that record exists.

Python 
# hooks/pre_tool_use.py
# Enforces: run_tests must succeed before post_review_comment.

def pre_tool_use(tool_name, tool_input, session):
    # 1. Record the prerequisite when it succeeds.
    if tool_name == "run_tests":
        result = session.run_tool(tool_name, tool_input)
        if result.exit_code == 0:
            session.state["tests_passed"] = True
        return {"decision": "allow"}

    # 2. Gate the dependent tool on recorded state — not on text.
    if tool_name == "post_review_comment":
        if not session.state.get("tests_passed"):
            return {
                "decision": "deny",
                "reason": (
                    "post_review_comment blocked: no successful "
                    "run_tests result recorded in this session. "
                    "Call run_tests first, then retry."
                ),
            }

    return {"decision": "allow"}

Notice what the hook keys off: the recorded outcome of the run_tests tool call — a structured, verifiable signal — not a sentence the model happened to write. That is the whole point. The invariant is checked against state the harness owns.

Deep Dive — The Feedback Loop

When a hook denies a call, the reason string is returned to Claude as the tool result. A well-written reason tells the model exactly what to do next ("call run_tests first, then retry"), so the agent self-corrects on the next turn. The hook is a gate, not a dead end — the workflow still completes, just in the required order.

The Anti-Pattern: Parsing the Model's Prose

A tempting but broken alternative: scan the assistant's text output for a phrase like "tests passed" and only permit the review comment once you see it. This fails for three independent reasons.

  • Wording is not fixed. The model might say "the suite is green," "all checks succeeded," or nothing at all.
  • Claims are not evidence. The model can assert tests passed without any tool call having run.
  • The signal is optional. If the model omits the sentence, your gate never opens — or opens on a false positive.
Anti-Pattern

Never make enforcement depend on how the model chose to phrase its output. If a check must be trustworthy, key it off the recorded tool result — verified in code — not off natural language.

Choosing the Right Enforcement Surface

The design tradeoff is worth internalizing. Prompts preserve flexibility; hooks guarantee invariants. Match the surface to the nature of the constraint.

Constraint type Right surface Guarantee Example
Tone, style, nuanced judgment System prompt / tool description Probabilistic "Write review comments in a constructive tone."
Preferred phrasing or format Tool description Probabilistic "Include the test summary in the comment body."
Preconditions & ordering PreToolUse hook Deterministic "No review comment before a passing test run."
Compliance / policy invariants PreToolUse hook Deterministic "Never call deploy without an approved change ticket."
Hard safety limits Hook + harness policy Deterministic "Deny writes to the production cluster."
Rule of Thumb

If a single violation is unacceptable, the rule belongs in code. If a violation is merely undesirable, it belongs in the prompt. When you find yourself strengthening a prompt to fix a reliability problem, you are operating on the probabilistic side of the line — exactly where the failure already occurred.

Key Takeaways

  • Prompts are suggestions; hooks are code. System prompts and tool descriptions shape model behavior probabilistically — they never guarantee it.
  • PreToolUse hooks intercept before execution. They run in the harness, inspect session state, and can deny a call — making the ordering constraint impossible to bypass.
  • Gate on recorded tool results, not on prose. Key enforcement off structured state the harness owns, never off how the model phrased its output.
  • Denials should teach. Return a clear reason so Claude runs the prerequisite step and retries — the workflow completes, in the required order.
  • Match the surface to the constraint. Use prompts for preferences and judgment; use hooks for invariants, preconditions, and compliance rules where a single violation is unacceptable.
  • When a prompt fails, don't strengthen it — relocate it. A reliability failure in the probabilistic layer is a signal that the rule belongs in code.
