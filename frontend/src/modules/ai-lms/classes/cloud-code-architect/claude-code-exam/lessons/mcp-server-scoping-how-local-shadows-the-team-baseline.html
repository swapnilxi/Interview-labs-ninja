MCP Server Scoping: How local shadows the team baseline

A structured-data extraction system depends on a shared MCP server. One engineer needs to test an experimental build — without touching the repository, and without leaking the experiment into every other project on their machine. This is a lesson about scope precedence, the deterministic mechanism Claude Code uses to resolve exactly that problem.

8 min read Intermediate

Learning Objectives

  • Explain the four MCP server scopes (local, project, user, plugin) and the audience each one serves.
  • Apply the precedence order local > project > user to predict which server definition wins.
  • Choose the correct scope to privately override a shared tool without editing version-controlled files.
  • Recognize why prompt-based workarounds (CLAUDE.md hints, renames) fail where scope shadowing succeeds.

The scenario, in one paragraph

You are building a structured data extraction system with Claude. It pulls fields out of unstructured documents, validates them against a JSON schema, and feeds downstream systems. The extraction logic lives in a team-owned MCP server — a Model Context Protocol server that exposes tools Claude can call. The team ships the baseline configuration in the repository's .mcp.json, checked into version control.

Now an engineer wants to try an experimental build of that same extraction server — but only in this one project, on this one machine. Teammates must keep loading the shared version. Which configuration approach achieves this?

Key Takeaway

The answer is local scope: register the experimental server under the same name at local scope. Local scope is private to one user and one project, and it outranks project scope for a same-named server — so it shadows the shared definition on this machine only.

Core concept: four scopes, four audiences

Claude Code does not merge MCP server definitions field by field. When the same server name appears at multiple scopes, the highest-precedence definition is used and the rest are ignored. That single rule is what makes private experimentation safe.

Scope Where it lives Who sees it Precedence
Local Current project entry in ~/.claude.json You, this project only Highest
Project .mcp.json at repo root Whole team (version controlled) Second
User User-level Claude config You, every project on this machine Third
Plugin / connector Installed plugin manifest Depends on install scope Lowest

The mental model is that each scope serves a different audience. Project scope is the team's committed baseline. Local scope is your personal override layer — the recommended home for experimental configurations. User scope is a machine-wide default that applies everywhere. Because local outranks project, a personal override never has to touch the shared file.

Local scope shadows the shared project definition on your machine only. Teammates never see the override.

Why the tempting alternatives fail

User scope — private, but wrong twice

Registering the experimental server at user scope feels private, and it is. But it fails on two counts: it applies to every project on the machine, not just this one — so you leak the experiment everywhere. And user scope sits below project scope in the precedence order, so the shared .mcp.json definition still wins in this project. The experimental build would never load where you actually wanted to test it.

Renaming inside .mcp.json — commits the experiment

Adding the experimental server under a new name to the shared file, then noting in CLAUDE.md that the project should prefer the experimental tools, exposes every teammate to experimental infrastructure and substitutes probabilistic prompt guidance for a deterministic configuration mechanism. Scope shadowing solves the same problem without changing anything the team sees.

Edit-and-revert on the shared file — one commit away from disaster

Editing the version-controlled .mcp.json to point at the experimental build, planning to revert before committing, puts experimental configuration one accidental commit away from the entire team. The scoping system exists precisely so personal overrides never require touching the shared baseline.

Warning

Never rely on "I'll revert it before I commit." Version control is not a scratchpad, and a forgotten revert turns a private experiment into a team-wide incident.

What the configuration actually looks like

The team baseline lives in the repository and is checked in. The experimental override lives in your home directory, keyed by the project path — private, and never part of the repo.

json — .mcp.json (team baseline, committed) 
{
  "mcpServers": {
    "extraction-server": {
      "command": "node",
      "args": ["./servers/extraction/dist/index.js"]
    }
  }
}
json — ~/.claude.json (local scope, private override) 
{
  "projects": {
    "/Users/you/code/extraction-pipeline": {
      "mcpServers": {
        "extraction-server": {
          "command": "node",
          "args": ["./servers/extraction-experimental/dist/index.js"]
        }
      }
    }
  }
}

Note that the server name is identical — extraction-server — in both files. That identity is what triggers shadowing. If you gave the experimental build a different name, both servers would load, and Claude would have to guess which tool to call.

Tip

When you are done testing, delete the entry from the local scope block in ~/.claude.json. The shared definition reasserts itself automatically — no revert, no commit, no coordination with the team.

Deep dive: why shadowing beats merging

Some configuration systems merge definitions field by field — command from one source, args from another. Claude Code deliberately does not do this for MCP servers. Merging would make it impossible to reason about which binary is actually running, and it would let a stray field from a lower scope silently alter a higher-scope server's behavior.

Instead, the rule is atomic: highest-precedence definition wins, whole. That atomicity is what makes the local-override pattern safe. You can never end up with a Frankenstein server whose command comes from local scope and whose args come from the team file.

Deep Dive

The full precedence order is: local > project > user > plugin-provided > connectors. When the same server name appears at multiple scopes, only the highest-precedence definition is used. See the Claude Code MCP documentation for the canonical rules and scope descriptions.

Key takeaways

  • Local scope is the recommended home for experiments. It is private to one user and one project, stored under the project's entry in ~/.claude.json.
  • Precedence is local > project > user (then plugin-provided servers and connectors). Same-named servers at multiple scopes resolve to the highest-precedence definition only.
  • Definitions are never merged field by field. The winning definition is used whole, so you can always reason about which binary is running.
  • Shadowing under the same name is the deterministic fix. Renaming the server or steering selection through CLAUDE.md substitutes prompt guidance for a configuration mechanism.
  • Never edit the shared .mcp.json for personal experiments. "I'll revert it before committing" is one forgotten commit away from a team-wide incident.
  • Cleanup is trivial. Delete the local scope entry when done — the shared definition reasserts itself with no coordination required.
